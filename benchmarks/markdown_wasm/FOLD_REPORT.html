Security report 2026-09-23 C, WebAssembly

markdown-wasm
Fold Index

One unsigned in the vendored md4c replaces a bounds check with a dead comparison. On a 64-bit native build it is a SEGV. In the WebAssembly artifact published to npm it is a bounded out-of-bounds read and a silent link-label confusion: 354 codepoints resolve references they do not name.

Summary

A signedness cleanup introduced in the fork broke the fold lookup

md_get_unicode_fold_info() searches three case-folding tables and stores the result of the binary search in a local. Upstream md4c declares it int and tests index >= 0. The vendored copy in markdown-wasm was changed to unsigned during a warning-silencing pass, which makes that test true for every value — including the -1 the search returns when the codepoint is in none of the tables. The pointer arithmetic two lines later therefore runs on 0xFFFFFFFF instead of returning early.

The consequence is not one bug but three, because the wild index is not the only thing that changed. The same branch returns unconditionally, so the second and third folding tables are never consulted at all; the read is a fixed pair of words chosen by the linker, so it is deterministic per build rather than random; and on wasm32 the oversized offset wraps inside linear memory, where it lands on real data instead of faulting. Section 4 separates the three; Section 6 says which of them survive a rebuild.

01

Root cause

src/md4c.clines 698–711, verbatim
 698    for(i = 0; i < (int) SIZEOF_ARRAY(FOLD_MAP_LIST); i++) {
 699        unsigned index;                          /* md4c 0.4.4: int index */

 701        index = md_unicode_bsearch__(codepoint, FOLD_MAP_LIST[i].map, FOLD_MAP_LIST[i].map_size);

 703            /* Found the mapping. */
 704            unsigned n_codepoints = FOLD_MAP_LIST[i].n_codepoints;
 705            const unsigned* map = FOLD_MAP_LIST[i].map;
 706            const unsigned* codepoints = FOLD_MAP_LIST[i].data + (index * n_codepoints);
 707
 708            memcpy(info->codepoints, codepoints, sizeof(unsigned) * n_codepoints);
 709            info->n_codepoints = n_codepoints;

md_unicode_bsearch__() returns -1 at md4c.c:510 when the codepoint is absent. With index unsigned, that -1 becomes 0xFFFFFFFF and survives the guard.

How it got there

The fork is md4c 0.4.4 plus 185 lines of changes, and the change set is recognisable as a compiler-warning cleanup. One warning in that pass is -Wsign-compare at md4c.c:1599 and :1604, where the label comparator reads if(a_fi_off >= a_fi.n_codepoints) — a_fi_off is OFF, which is typedef unsigned MD_OFFSET, while n_codepoints was int. The fix taken was to make the structure field unsigned. That turned index * n_codepoints into a mixed-sign expression, so the local index was made unsigned as well — and the guard silently died.

md4c 0.4.4 → src/md4c.cthe whole signedness pass

A project-wide scan for the same shape — an unsigned local compared against zero — finds exactly one other candidate, md4c.c:222, whose comparison sits behind an MD_ASSERT and is harmless. This is the only exploitable instance of the class in the tree.

Three other changes in the fork are unrelated and are not defects: a genuine fix to ISANYOF_ (it now rejects '\0', which md_strchr used to match against the terminator), the removal of an unused n_lines parameter from four functions, and one extra next_index step in md_resolve_links().

02

Reachability

The path is taken by any codepoint above 0x7f that is not itself a fold source in FOLD_MAP_1 — which is most of the non-Latin world. The shortest way in is a link reference definition whose label holds one such codepoint; no malformed input is required:

minimal inputsboth crash a 64-bit native build
# 5 bytes of valid UTF-8 — a link reference definition
5b e4 b8 ad 5d 3a 20 2f 78          ["[中]: /x"]

# 8 bytes of malformed UTF-8 — md_decode_utf8__ returns (unsigned) str[0],
# so 0xAC sign-extends to 0xFFFFFFAC and becomes the label's codepoint
5b ac ac ac ac 5d 3a 78             ["[\xAC\xAC\xAC\xAC]:x"]

A definition is required, not just a use: label folding runs when the definition table is built and when a reference is looked up. [café]: /menu followed by a reference to it is enough, and so is an ordinary document with an accented or CJK reference label.

FOLD_MAP_2 and FOLD_MAP_3 are unreachable

Because index >= 0 is always true, the branch is taken on the very first iteration and returns at :723. Iterations for FOLD_MAP_2 and FOLD_MAP_3 never run, so every multi-codepoint case fold is dead regardless of the framework — a property of control flow, not of the corrupted value. [ß] and [ss], [ẞ] and [ss], [İ] and [i̇], [ﬁ] and [fi], [ﬅ] and [st] no longer match each other anywhere.

03

What the wild index actually reads

index is always exactly 0xFFFFFFFF, and n_codepoints is always 1, 2 or 3 from the static table. The addresses are therefore data − 4 and map − 4: the single word immediately before each array. Which word that is comes from the linker's data layout, so the corrupted fold value is fixed per build and does not depend on the input at all.

In the shipped markdown.wasm both words can be read straight out of live linear memory, and both are explained by the layout:

Layout of the folding tables in the shipped artifact

0x0D00–0x0D1FWHITESPACE_MAP (8 words, md4c.c:521)—
0x0D1CWHITESPACE_MAP[7] = S(0x3000)0x00003000  ← map − 4

0x116Cthat padding, zero0x00000000  ← data − 4

The two adjacent objects are contiguous with no padding — WHITESPACE_MAP ends exactly where FOLD_MAP_1 begins — which is why the read lands on the whitespace table's last entry rather than on unrelated bytes. Substituting the two values into info->codepoints[0] += codepoint − (map[index] & 0x00FFFFFF) at md4c.c:719 gives the whole behaviour in one line:

the shipped artifact's fold functionstable across five workloads
folded(c) = c − 0x3000        for every codepoint above 0x7f outside FOLD_MAP_1

Codepoints inside FOLD_MAP_1 still fold correctly, and ASCII takes the fast path at md4c.c:689 before any of this. Everything else — including the lower-case member of every case pair, which is never a fold source — folds to a value derived from a subtraction that should never have happened.

04

Three faces of the same token

Native, 64-bit

Out-of-bounds read at +16 GB, then SEGV

Availability

The product index * n_codepoints is 32-bit unsigned, so it is zero-extended to ptrdiff_t and the offset becomes +4 294 967 295 elements — 17 179 869 180 bytes. The memcpy at :708 faults immediately.

Any process parsing untrusted Markdown with the C sources built for x86-64 dies on input of a few bytes. libFuzzer with -fsanitize=address,undefined found it in the first 60-second run.

wasm32

Bounded out-of-bounds read inside linear memory

Memory safety

In wasm the pointer index is an i32 read as signed, so the same expression wraps to −4 bytes and lands on the alignment padding described above. Up to 12 bytes are read from before the array, and FOLD_MAP_1[-1] is read at :711 as well. No trap, no fault, no leak.

Emscripten's SAFE_HEAP checks the address against the linear-memory bounds rather than the object, and the address is inside them, so the debug build does not trap either. This is undefined behaviour that the platform absorbs.

wasm32, shipped npm build

Link-label confusion — 354 codepoints alias other labels

Correctness, fail-open

folded(c) = c − 0x3000 makes link labels compare equal when CommonMark says they differ. A definition labelled [A] is resolved by the reference [ち]; a definition labelled [À] by [ム]; a definition labelled [Α] by [㎱].

Fail-open matching is the dangerous direction for anything that keys trust on reference definitions. The 26 Hiragana codepoints are ordinary Japanese characters, so this also mislinks ordinary Japanese documents with no adversary involved.

06

What survives a rebuild

The constant 0x3000 belongs to this particular binary. A future build of the same sources may place different objects around the arrays, and the alias table would change with it — so the exact list in Section 5 should be recomputed for any artifact you care about. The other findings do not depend on the layout, and neither does the broken behaviour in the general case:

  • ✗Multi-codepoint folding (FOLD_MAP_2, FOLD_MAP_3) is dead in every build — the branch returns at the first iteration whatever the value read is. Demonstrated on a 32-bit build whose two words are both zero, so its fold function is the identity: [ß] and [ss] still fail there.
  • ✗The out-of-bounds read and the 64-bit SEGV are present in every build, independent of what the words contain.
  • ✗Any non-ASCII label whose fold is not itself (that is, the lower-case member of every case pair) gets a corrupted value whenever the offset is non-zero.
  • ✓With a zero offset — as in the 32-bit build measured here — the corruption is the identity function and the single-codepoint cases happen to behave correctly. A rebuild could land there.
Correcting an earlier measurement

A 32-bit native build is a useful proxy for pointer width and a misleading one for values. The -m32 build used during this investigation has WHITESPACE_MAP and FOLD_MAP_1 arranged so that both stray words are zero, which is why it renders everything correctly while the shipped artifact does not. Both facts were read from the binaries rather than assumed.

07

Fix

Restoring the type the guard depends on removes all three consequences at once. This was verified: a build of the same sources with only this change applied resolves [Ä]/[ä], [ß]/[ss] and [ﬁ]/[fi] correctly, and no longer resolves [A] against [ち].

src/md4c.c:699the fix
-            unsigned index;
+            int index;

Two notes for whoever applies it. The warning that provoked the original change is real, so it will come back; silence it where it belongs, by casting at the comparison rather than by changing the field type:

md4c.c:1599 and :1604the warning to keep quiet locally
-        if(a_fi_off >= a_fi.n_codepoints) {
+        if(a_fi_off >= (OFF) a_fi.n_codepoints) {

And the field itself should go back to int as well. Restoring index alone is sufficient, but leaving n_codepoints unsigned keeps index * n_codepoints a mixed-sign expression, which is exactly the shape that invited the change in the first place.

09

Method, provenance and standing caveats

Provenance

The file analysed is src/md4c.c at commit 0d99d1151ff4d929a8ac8f3a191bfec54a10a869 (blob 52884ebcdf770682672ab778a6d9868de759bdd3), which is still master HEAD as of 2026-09-23 — the commit dates from 2021-07-06 and nothing has landed since. The build inputs are unchanged from upstream: wasmc.js compiles with -DMD4C_USE_UTF8 for release, so the shipped artifact takes the same MD4C_USE_UTF8 path as the native builds here. The npm tarball for 1.2.0 is byte-identical to the committed dist/ in both markdown.wasm (0e3e932f…) and markdown.node.js (56aab5e1…), so installed copies are affected, not just the repository. Comparing against md4c tags puts the base at release 0.4.4 — 185 changed lines.

How it was found

Not by reading the diff. A harness generator produced an md_parse libFuzzer entry point for this project; its 60-second smoke run at 47 227 execs found the SEGV reported at md4c.c:708. The generated harness was cleared of suspicion by reproducing the crash with a hand-written reference harness carrying the same call, which is what made the finding attributable to the target. The three impacts, the alias count and the layout explanation came afterwards, from reading the 185-line fork diff and then measuring the shipped artifact directly.

What is verified, and what is not

Verified. Every behaviour in the Section 5 table, on the npm artifact and against upstream md4c 0.4.4. The two stray words, read from live linear memory in the artifact and stable across five different workloads. The two words in the 32-bit build, read from its .rodata. The one-token fix restoring all three impact classes.

Not verified. Impact in any specific application. The fail-open matching is a real deviation from CommonMark and it is severe in principle for a caller that keys trust on reference definitions, but no end-to-end exploit against a real consumer was built here, and severity beyond "wrong link target" is a property of the caller, not of the library. The SAFE_HEAP claim in Section 4 is a reading of what that check does — bounds against linear memory — rather than a test of a debug build.

Disclosure

The defect is unpatched in the current master of rsms/markdown-wasm and in the 1.2.0 npm release, and it is not a bug in md4c upstream, whose own users are unaffected. The natural route is an issue or private report to the repository, noting that dist/ must be rebuilt from the fix for the published artifact to change.
